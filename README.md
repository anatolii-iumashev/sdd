# SDD Skill

Этот навык помогает вести разработку через спецификации: от идеи до финальной реализации и архивирования результатов.

## Что это такое

SDD (Spec-Driven Development) — подход, при котором фича или изменение сначала описывается в виде RFC/спецификации, затем реализуется по этому описанию, а после завершения — фиксируется итоговая сводка.

Такой процесс помогает:
- снизить неопределённость и разночтения;
- зафиксировать цели, ограничения и критерии приёмки;
- вести работу по понятному и повторяемому циклу;
- оставлять после завершения фичи понятную документированную историю.

## Компактная спецификация (~1000 слов)

RFC стараемся укладывать в ~1000 слов. Рабочий паттерн — две сессии: 
- в одной пишем сжатую спеку RFC - если надо обсуждаем в команде или с заинтересованными лицами (стейкхолдерами)
- в чистой сессии скармливаем её кодинг-агенту. 

Компактный RFC — это весь контекст исполнителя, без шума и истории переписки. Не уместились в ~1000 слов — повод декомпозировать фичу на несколько RFC.

Почему? Есть проблема контекстного окна:
• Заявленный context window: 1M+ токенов
• Usable context window: ~100–150K токенов — вырос лишь на ~20%
• После 200K токенов модель начинает «чудить»; после 350–500K — «make it worse»
• Lost in the middle syndrome: модель забывает середину, потом начало
• LLM плохо понимают, что важно → автоматическая компрессия контекста теряет критичное

Искусство маленьких шагов через RFC - помогает обойти эту проблему и получить максимум из имеющихся ресурсов.

## Цикл работы

1. RFC — описать проблему, цели, решение и критерии приёмки.
2. Implement — реализовать фичу по RFC и проверять её по приёмочным критериям.
3. Apply — зафиксировать итоговую сводку и перенести RFC в архив.

## Под-скиллы

- sdd-rfc — создать RFC/спеку для новой фичи или изменения.
- sdd-implement — начать реализацию по существующему RFC.
- sdd-apply — завершить работу, заархивировать RFC и сохранить итоговую спецификацию.

## Когда использовать

Этот навык полезен, когда нужно:
- описать новую фичу перед разработкой;
- структурировать техническое задание или design doc;
- вести изменения по понятному процессу;
- сохранить историю решений и результатов для будущего.

## Типовая структура документов

- активные RFC: docs/rfc/<slug>.md
- архив RFC: docs/rfc/archive/<slug>.md
- итоговые спеки: docs/specs/<slug>.md

## Коротко

Если у вас есть идея или изменение, которое хочется довести до релиза без хаоса — начните с RFC, затем реализуйте по нему, а после завершения зафиксируйте итог.
